# revops-capital — entry points

This crate is a **decision kernel with no caller today**. Nothing in
`crates/revops/src/main.rs` or any other crate calls into it. This file
enumerates every entry point the plugin would need to wire up, so this port
does not become a fourth instance of the "ported kernel, never called"
failure mode this project has been burned by three times already.

Per the task's hard rules, this crate makes **zero** live Lightning RPC
calls, opens **zero** production databases, and sends **zero**
payments/opens/closes. Every function below takes pre-fetched, typed
evidence and returns a decision or a plan; wiring the evidence-gathering
(RPC calls) and the plan-execution (RPC calls) is explicitly **NOT DONE**
and is out of scope for this pass.

## Entry points this plugin will need — NONE are wired yet

Every one of these requires a caller in `crates/revops/` (or wherever the
capital-allocation loop eventually lives) that:
1. gathers the evidence via CLN RPC / `revops-db` reads,
2. calls the pure function,
3. for money-committing decisions, executes the RPC (fundchannel/close/
   Boltz swap) and reserves/settles/releases budget around it.

None of step 1 or step 3 exists. This crate only does step 2.

### Capex budget

- **`capex::compute_allocations`** — needs a per-cycle evidence gather:
  `analyze_all_channels()`-equivalent profitability read, bleeder status per
  channel, `get_total_capex_by_channel(30)`, `get_spend_ledger_summary(30)`,
  confirmed on-chain balance, capital-efficiency snapshot. **Not called
  anywhere.** Would be invoked once per capacity-planner cycle (py: inside
  `CapacityPlanner.execute_cycle`'s fee-gate-then-budget flow) and by a
  future `revenue-capex-status` RPC (Python still owns this RPC; see
  port-map lens "plugin entrypoint", `spend-budget-and-capex-rpcs`, marked
  `[ ]` in `docs/port/PARITY-CHECKLIST.md` Lens 0).
- **`boltz_reservation::*`** — ready to call from a future Boltz swap
  execution path once one exists in Rust (today: none — `BoltzCliManager`
  is entirely unported, see below). The reservation lifecycle is otherwise
  inert.

### Capacity planner pure kernels

All of these are called, in Python, from inside `CapacityPlanner.execute_cycle`
(py `modules/capacity_planner.py` 363-786) — a large orchestration method
this port does **not** attempt (see "Deliberately not ported" below). Until
`execute_cycle`'s Rust equivalent exists, these functions have no caller:

- **`portfolio_gate::check_portfolio_balance_gate`** — first gate
  `execute_cycle` runs every pass; needs a `listpeerchannels` fetch.
- **`close_fee::*`** — needed by any future close-execution path (py
  `_execute_close`, `_execute_defibrillation`'s fee estimation) and by a
  future `revenue-rebalance-debug`/planner-status RPC surface.
- **`dead_capital::advance_dead_capital_stage`** — needs the
  `dead_capital_stages` DB table (schema exists in Python; `revops-db` does
  not have this table today — **no Rust reader/writer**). The
  `close_protection` input, however, CAN be populated for real:
  `revops_analytics::protection::close_protection_reason` is already a
  full, tested port of `protection_service.close_protection_reason` (same
  gate order, same pinned reason strings). A caller just needs to build its
  `ProtProfEvidence`/`FlowEvidence` inputs and pass the result straight into
  this kernel's `close_protection` field — that wiring is the missing
  piece, not the protection logic itself.
- **`ev::calculate_open_ev` / `calculate_redeployment_ev` /
  `calculate_recycle_ev` / `is_recycle_eligible`** — need: peer
  closed-channel profit history, the node's observed daily ppm (a fleet-wide
  aggregate Python caches per cycle), feerate RPC, peer inbound-fee history,
  current block height, policy-protected-peer set, route-pair SCID set.
  None of these evidence sources have a Rust reader today outside the fee
  subsystem's own (differently-shaped) evidence gathering.
- **`gates::failed_open_backoff_reason` / `peer_exposure_cap_reason`** —
  need `planner_actions` / `listpeerchannels` reads. The `planner_actions`
  table has no Rust reader.
- **`scoring::normalize_candidate_scores` / `apply_pool_quotas`** — need the
  candidate pool itself, which is built by the five discovery strategies
  (`_discover_from_winners`, `_discover_from_neighbors`,
  `_discover_from_graph`, `_discover_from_route_pairs`,
  `_discover_from_demand_flow`) — **none ported**, all RPC/DB-heavy.

## Deliberately NOT ported in this pass, and why

- **`CapacityPlanner.execute_cycle`** and its 5 candidate-discovery
  strategies (py 363-786, 1485-1949 approx) — the top-level orchestration
  loop. It is RPC-heavy end to end (listpeerchannels, listnodes, listchannels,
  fundchannel, close) and stitches together every kernel above plus several
  not ported at all (LN+ evaluator competition for the open slot, Boltz
  coordination). Porting the orchestration without the kernels it calls
  being wired to real evidence would not reduce risk — it would just move
  the "kernel with no caller" problem up one layer.
- **`_execute_open` / `_execute_close` / `_execute_defibrillation` /
  `_rpc_fundchannel` / `_rpc_close`** (py 3054-3973) — these send real
  `fundchannel`/`close`/rebalance RPCs. Hard rule #2 forbids this crate from
  ever calling them; a future porting pass must add these in a
  clearly-marked, RPC-only shim layer, never inside this crate's pure
  kernels.
- **`BoltzCliManager`** (py `modules/boltz_manager.py`, ~2,670 LOC) — a
  `subprocess` wrapper around an external `boltzcli` binary with three
  separate locks, bech32/blech32 address validation, and its own layered
  budget gates. Named as a separate component in the port-map lens; large
  enough to be its own porting project. **Zero Rust code exists for it.**
- **`BoltzAutoCycle`** (py `cl-revenue-ops.py`, ~1,400 LOC) — the in-plugin
  orchestrator that picks treasury/balance/idle mode and drives
  `BoltzCliManager`. Depends entirely on the above. **Not ported.**
- **`LNPlusSwapAutomation`** (py `modules/lnplus_swaps.py`, ~2,099 LOC) —
  `LNPlusClient` + `SwapEvaluator` + `SwapLifecycle`: HTTPS API client with
  signmessage auth, a 15-gate evaluator, and an irreversible-obligation
  state machine (48h fundchannel deadline once a swap application is
  filled). This is real money on a hard deadline and deserves a dedicated,
  carefully-reviewed port, not a rushed inclusion here. **Not ported.**
- **`CapacityPlanner._identify_winners` / `_identify_losers`** (py 805-1129)
  — the winner/loser classification loop. This was evaluated for porting
  but declined: in Python it does SEVEN separate inline DB/analyzer calls
  per channel per cycle (rebalance success rate, diagnostic rebalance
  stats, fee-strategy state for the DTS posterior mean, peer uptime, bleeder
  list, route-pair list, capital-efficiency snapshot) interleaved with the
  decision logic, and calls `_close_protection_reason` (now available —
  `revops_analytics::protection::close_protection_reason`, see above) and
  `_check_defib_allowed` (policy-manager-dependent; no Rust equivalent)
  mid-loop. Restructuring this into a clean `(evidence) -> classification`
  pure function is a substantial, self-contained task that deserves its own
  session with its own fixture-generation pass — bolting it on here under
  time pressure risked exactly the kind of subtle behavioral drift this
  project's parity discipline exists to prevent (see the
  `extract_actual_close_fee_sats` dead-code quirk documented in
  `src/planner/close_fee.rs` as a concrete example of a real bug this
  discipline caught in a MUCH smaller function). The four sub-decisions that
  *were* extracted cleanly and are ported: portfolio gate, close-fee
  planning, the dead-capital stage machine, and the EV/recycle-eligibility
  math.
- **`_score_candidate`** (py 2110-2201) — candidate enrichment: six
  independent DB/RPC lookups (peer reputation, closed-channel profit
  inheritance, peer uptime, node address lookup for clearnet detection,
  historical inbound fee, cached peer channels for large-channel bonus) plus
  in-memory demand-flow-profile lookups, ending in a single multiplicative
  score. Declined for the same reason as winners/losers: restructuring it
  into pure typed evidence is straightforward in principle but was not done
  under this session's time budget, and a half-verified version would be
  worse than an honest gap.

## Fixture generation

`tools/port/gen_capex_fixtures.py` and
`tools/port/gen_capital_planner_fixtures.py` import
`modules/capex_budget.py` / `modules/capacity_planner.py` directly from
`/home/sat/bin/cl_revenue_ops` (unmodified) and drive the REAL Python
methods against constructed stub `profitability`/`database`/`config`
objects (plain `types.SimpleNamespace` duck-typing — no CLN, no real DB).
Output is committed at `fixtures/capital/capex/allocations.json` (26
scenarios) and `fixtures/capital/planner/kernels.json` (82 scenarios across
11 function kinds). Re-run either script and diff against the committed
fixture to re-verify parity if the Python source changes.
